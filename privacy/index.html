Privacy Policy

Last updated: 11 September 2026

RangeGate handles unsigned drafts of transfer pricing studies — client-confidential material by nature. This policy describes what the system actually does with it. Where the design stores nothing, that is stated plainly, because it is enforced in the code and in the database schema, not just promised here.

1. There are no accounts

RangeGate has no sign-up, no login and no user profiles. We never ask for your name, your email address, your firm, or your client's identity. The “file reference” field on the check form exists only to label the PDF generated in your browser; it is never sent to the server.

2. The anonymous check: computed, returned, discarded

When you run the free check, your browser sends the figures you entered — the assessment year, method and PLI, comparable margins, tested party financials, transaction lists with their IDs, values and short descriptions, and group threshold figures — to our verification API in a single request. The engine recomputes the statutory mechanics and returns the verdicts in the response.

None of that input is stored.The demo path performs no write of the study data: no database insert, no file, no log line containing your figures. The API's logging rule explicitly forbids logging the input, and the only things the demo writes are the two items described in sections 3 and 4 below — a salted hash for rate limiting and an anonymous counter. When the response reaches your browser, the server holds nothing of your study.

Practical consequence: avoid pasting information the check does not need. The engine works on figures; party names or narrative text are not required for any verdict (the free-text transaction description is optional and capped at 200 characters — it, like the rest of the demo input, is processed and discarded).

3. Signed records: six fields, no figures

When a run is signed, exactly six fields are stored, and the database schema is built to abort any change that would add a seventh:

  • the record's hash (an HMAC-SHA256 signature)
  • the time it was issued
  • the assessment year (e.g. “2025-26”)
  • the engine version that computed it
  • the identifier of the signing key
  • the verdict counts (how many PASS / FAIL / NEEDS REVIEW / UNMATCHED)

A signed record stores no margin, no percentile, no arm's length range, no transaction or adjustment amount, no tested-party financials, no comparable name or figure, no taxpayer or associated-enterprise name, no file, no IP address, and no free text. This is deliberate: records are publicly checkable at /verify by anyone holding the hash, so the record is designed to be worthless to read — it cannot leak, or be compelled to disclose, what it does not contain. Records are retained indefinitely, because their purpose is to remain verifiable.

4. IP addresses and rate limiting

The anonymous demo allows 10 runs per hour per network, record signing is capped at 60 per hour per network, and a global daily cap bounds total demo usage. To enforce this, the API derives a one-way SHA-256 hash of your IP address combined with a secret salt that never leaves the server, and counts requests against that hash. Your raw IP address is never stored and never logged — the rate-limit table structurally rejects anything that is not a 64-character hash, and without the salt the hash cannot be reversed into an IP. Rate-counter rows are garbage-collected after 48 hours.

5. No cookies, no analytics, no trackers

This site sets no cookies, uses no local storage, loads no third-party analytics, no tracking pixels, no ad scripts and no external fonts or CDNs. The only network requests the pages make are to our own verification API. PDFs are generated inside your browser, not on a server.

The API keeps anonymous, aggregate funnel counters (for example: a demo was run, a record was signed) whose metadata is limited to outcome codes such as verdict counts. The database rejects, by constraint, any counter that would carry study data, an identity, an IP or a record hash — so a counter can never be joined back to a person or a record.

6. Who processes the data, and where

The verification API and its database run on Supabase, on infrastructure located in the United States (AWS region us-east-2). Requests to the API therefore transit Supabase's platform, which is operated under Supabase's own privacy and security terms. The website itself is served as static files and runs no server-side code of ours.

7. Contact and requests

RangeGate is in early access and a dedicated contact channel (own domain and mailbox) is still being set up; we will not print an address here that does not exist yet. This page will be updated with a working contact address, and the “last updated” date will change when it is.

In the meantime, note what a deletion request would even apply to: demo input is never stored, no account exists, IPs are stored only as unlinkable salted hashes that expire within 48 hours, and a signed record contains no personal data and is identified only by a hash that we cannot connect to you. The system is built so that there is, as far as practicable, nothing about you to hand over or to delete.
